# `features/admin/` — administrator screens

Routes: `/admin/inicio` (landing page), `/admin/agenda`, `/admin/urgencias`, `/admin/agenda-pendiente`, `/admin/especialistas`, `/admin/horarios`, `/admin/cursos`, `/admin/asesorias`. Every write goes through `AgendaApi` and is re-validated by Postgres; the screen only presents results.

- **Menu** (`layout/marco.ts`): Inicio, then the groups «Atención» (Urgencias, Agenda, Agenda pendiente), «Solicitudes» (Cursos, Asesorías) and «Configuración» (Especialistas, Horarios).
- **Inicio** (`inicio.ts`, migration 28): one call to `admin_inicio` (pending emergencies, appointment requests, enrolments, advice requests, today's non-cancelled appointments in Bogotá time). Each card links to its screen with a query param (`?estado=pendiente`, `?dia=YYYY-MM-DD`) read through `input()` aliases in `ngOnInit`. Count nothing in Angular.
- **List + detail** (`lista-detalle.ts`, user's decision): Urgencias, Agenda pendiente, Cursos and Asesorías show a compact list with the detail panel beside it (never tables or dialogs). The screen maps its data to `FilaLista` and projects an `<ng-template let-id>`; the component auto-selects on wide screens, swaps list/detail under 1000 px, moves focus and recreates the panel per id. Detail components take `input()`s, use the host class `detalle-panel` plus the global `.detalle-cabecera`, `.destacado`, `.gestion`, `.datos` styles, and need an `h2 tabindex="-1"`. **No inner scrollbars** (user's request): list and panel grow with the page (only the page scrolls); the list is paginated client-side, 8 rows per page (`porPagina`), each row is its own card with 8 px between rows (and 8 px between list and panel); keep panels compact — each `.datos` pair is wrapped in a `<div>` (label above value, columns that auto-fit) and filter buttons share the row (`.fila.fila--filtros`). Rows need `align-items: stretch` (buttons otherwise grow to the text width). `.pagina` leaves 8 px at the bottom. Panels that write expose `ocupado` (the screen blocks the list meanwhile) and emit `cambiada`.
- **Conflicts:** changing weekly hours, saving a block or deactivating a specialist can fail with `ErrorConflicto` (future confirmed appointments would be stranded). Catch it and call `mostrarConflictos()` (`conflictos.ts`), which lists the affected appointments. Never cancel appointments to make a change pass.
- **Weekly schedule:** the editor replaces the whole week with one `admin_set_weekly_schedule` call. Do not delete + insert from the client: the deferred conflict check would reject the intermediate state. Client-side validation (overlaps, end > start) is only a convenience.
- **Blocks:** `formulario-bloqueo.ts` converts "all day" ranges to `[00:00, next day 00:00)` in Bogotá time; notes must not contain health data.
- **Creating specialists** (`formulario-especialista.ts`) calls the `admin-users` Edge Function (invite by email → the person sets their own password at `/restablecer`). New specialists have no hours until configured in Horarios, so they offer no slots.
- **Access for existing specialists** (migration 29): specialists without `profile_id` get «Generar enlace de acceso» → `admin_crear_invitacion` → `enlace-invitacion.ts` shows `<origin>/invitacion#<token>` once (copy / WhatsApp). «Nuevo enlace» revokes the previous one; «Anular enlace» → `admin_anular_invitacion`. The public page is `features/acceso/invitacion.ts`.
- **Known gaps:** the modal only creates *new* specialists (by email invitation). Removing a specialty from a specialist with future appointments of that specialty is not validated.
- **New appointment** (`nueva-cita.ts`): patients are identified by document type + number (phone is contact only and may repeat); an existing patient's names are shown and never overwritten; the "autorización de datos" checkbox is required. `selector-cupos.ts` shows the real free slots (via `admin_free_slots`) in 14-day windows and keeps the dialog's choice as an ISO instant.
- **Cursos** (`cursos.ts`, migrations 20 and 30): there is no courses table. The catalog is the chatbot menu (`bot_nodos`: `info` nodes under a branch with `accion = 'inscripcion'`; the branch is the category, an intermediate submenu the "grupo") and the enrolments are `bot_inscripciones`; both belong to the chatbot engine and are read only through `AgendaApi.cursos()` / `inscripciones()` → `admin_cursos` / `admin_inscripciones`. Never query `bot_*` tables directly or add policies to them. The screen shows the filters and the list + detail (the catalog cards were removed at the user's request); the catalog just fills the «Categoría» and «Curso» filters.
- **Asesorías** (`asesorias.ts`, migrations 21 and 30): same pattern as Cursos. Catalog = `info` nodes under the menu branches with `accion = 'servicio'` (Asesoría jurídica, Asesorías generales; the «Simposios y bienestar empresarial» submenu is a group inside generales). Requests = `bot_solicitudes` with `tipo = 'servicio'` only (that table also stores appointment requests and emergencies, which must not appear here). A request linked to a branch instead of a specific type shows as «<rama>: sin tipo específico». `detalle-solicitud.ts` shows the case text (`detalle`), which may be sensitive (Ley 1581): admin only.
- **Status management in Cursos and Asesorías** (migration 30, user's request): tabs (`pestanas-gestion.ts`) «Por confirmar» (pendiente, contactado), «Confirmados» (matriculado / agendada, atendida) and «Cancelados»; the grouping is applied in Postgres (`agenda.vista_gestion`, `p_vista`) and mirrored in `ESTADOS_*` only to build the status filter. Counts: `admin_conteo_gestion`. The detail panel uses `gestion-estado.ts` → `admin_cambiar_estado_inscripcion` / `admin_cambiar_estado_asesoria` (`status_changed` guard). Changing status sends nothing to the person.
- **Agenda pendiente** (`agenda-pendiente.ts`, migrations 24–25): «open» appointment requests the bot saves when it cannot book online — the person types the day/time they prefer (`preferencia`). They are `bot_solicitudes` with `tipo = 'cita'` (motivo: «Sin agenda en línea» for services without specialists such as Fonoaudiología, Optometría and Fisioterapia; «Atención a domicilio»; «Error al agendar automáticamente»; or a reschedule with no free slots, which has no menu service and shows under «Otros»). The screen shows **only the filters and the list + detail** (no catalog cards — the user asked to remove them). `serviciosCita()` just fills the «Servicio» filter (health services = `info` nodes under the menu's `accion = 'cita'` branch, `agenda.servicios_cita_nodos()`); its `agenda_en_linea` / `pendientes` columns are currently unused by the UI. Read through `AgendaApi.serviciosCita()` / `citasPendientes()` → `admin_servicios_cita` / `admin_citas_pendientes`. The admin changes each request's status (any of the five) from the detail panel `detalle-cita-pendiente.ts` → `AgendaApi.cambiarEstadoCitaPendiente()` → `admin_cambiar_estado_cita_pendiente`; it sends the status being viewed, so a concurrent change returns `status_changed` and the list reloads. Changing status never books an appointment nor notifies the patient; these requests are not appointments until staff book them in Agenda.
- **Urgencias** (`urgencias.ts`, migrations 26–27; list + detail layout chosen by the user because cards got crowded): `bot_solicitudes` with `tipo = 'urgencia'`. Tabs Sin atender / En gestión / Historial, name/document search and sede/domicilio filter, all resolved in Postgres (oldest wait first; history newest first). Uses `lista-detalle.ts` with `detalle-urgencia.ts` as the panel; the screen keeps unsent note drafts per id and disables list and tabs while it saves. The panel changes status (`status_changed` guard) and appends follow-up notes (never edited or deleted; saving a status also saves a typed note). Contact links in `contacto.ts`. The menu badge and tab counts come from `core/urgencias-resumen.service.ts` (polled every minute by `layout/marco.ts`, admin only; polling does not count as user activity) and the list reloads when the figures change. No status-change history (so no «atendidas hoy») and no external alert yet (both postponed by the user). `detalle` is health data: admin only.
- Cursos and Asesorías share `agrupar-catalogo.ts` (generic grouping by category, display only; used for the «Categoría» filter and the results title). No screen shows catalog cards anymore; the global classes `.contador` and `.titulo-resultados` remain in `styles.scss`.
- Dialogs are one component per file (`nueva-cita`, `reprogramar-cita`, `cancelar-cita`); reschedule is atomic server-side, so a failed new slot leaves the original appointment untouched.
